# 여행 플래너 앱 PRD v1.0

Oct 24, 2026 · @Jin

## 0. 개요

**한 줄 정의:** 취향·인원·일수·예산을 넣으면 실제 교통 시간표 기준으로 하루 동선을 짜 주고, 현지에서는 다음 할 일과 길 안내를 보여 주며, 일정이 바뀌면 경로와 시간을 자동으로 다시 맞추는 여행 앱.

이 문서는 Claude Code가 그대로 구현을 시작할 수 있도록 결정을 확정한 개발용 PRD다. 화면 시안은 디자인 캔버스 "여행 플래너 앱 프로토타입"의 C1 줄을 기준으로 한다. 화면 속 시간·요금·후기는 모두 예시 데이터다.

**해결할 문제**

1. 자유여행 계획에 시간이 너무 많이 든다 (장소 고르기, 동선, 교통, 영업시간 확인).
2. 기존 일정 앱은 실제 교통 시간표와 영업시간을 반영하지 않아 현지에서 틀어진다.
3. 현지에서 일정이 바뀌면 (지연, 취소, 체력) 남은 일정을 다시 짤 방법이 없다.

**MVP 성공 지표 (출시 후 90일 목표치)**

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| 일정 완주율 | 생성한 일정 중 마지막 날 도착 체크까지 간 비율 | 40% |
| 현지 사용률 | 여행 기간 중 하루 1회 이상 앱을 연 사용자 비율 | 70% |
| 경로 정확도 | 코스 평가에서 "노선·시간이 정확했어요" 응답 비율 | 85% |
| 코스 평가 응답률 | 하루 종료 후 평가를 제출한 비율 | 30% |
| 예약 전환 | 일정 내 예약 버튼 클릭 → 제휴사 이동 비율 | 일정당 15% |

**비목표 (MVP에서 하지 않음)**

- 항공·숙소 검색과 자체 결제 (세계여행의 도시 간 이동은 예상 시간·가격 + 제휴 검색 링크로 처리, 13장)
- 전 세계 동시 지원 (도쿄 먼저)
- 커뮤니티 피드, 친구·팔로우
- 구독 결제
- LLM이 일정 수치(시간·요금·순서)를 직접 생성하는 방식

**확정된 핵심 결정**

| 항목 | 결정 |
| --- | --- |
| 화면 방향 | C1 "한 화면 한 행동" 구조 + 길 안내의 접고 펴는 지도 + 전체 화면 지도 |
| 출시 도시 | 1차 도쿄, 2차 오사카 |
| 앱 | Expo(React Native) + TypeScript, iOS·Android 동시 |
| 서버 | Python 3.12 + FastAPI, PostgreSQL 16 + PostGIS, Redis |
| 경로 계산 | OpenTripPlanner 2 자체 운영 (GTFS + OpenStreetMap) |
| 지도 표시 | MapLibre + OpenStreetMap 기반 벡터 타일 |
| 일정 엔진 | 규칙·점수 기반 결정적 알고리즘 (5장), LLM 미사용 |
| LLM 사용 범위 | 장소 태그·설명문 일괄 생성(배치)만. 런타임 일정 계산에는 쓰지 않음 |

## 1. MVP 범위와 기술 스택

MVP는 도쿄 한 도시에서 "설정 → 일정 생성 → 현지 실행 → 자동 조정 → 평가" 한 바퀴가 완전히 도는 것이다. 장소는 도쿄 23구 기준 300곳(유명도 1\~5 등급 고르게)으로 시작한다.

**단계별 범위**

| 기능 | MVP (1단계) | 2단계 | 3단계 |
| --- | --- | --- | --- |
| 여행 설정 (4단계 질문) | O |  |  |

**저장소 구조 (모노레포)**

```

/services/api       FastAPI 서버
/services/engine    일정 엔진 (Python 패키지, API가 import)
/packages/engine-ts 일정 엔진 TypeScript 포트 (앱 오프라인 재계산·웹 공유)

/data/pipelines     GTFS·장소 수집·태깅 배치
/infra              docker-compose, OTP 설정
/docs               이 PRD
```

## 2. 정보 구조

처음 한 번 여행을 설정하면 이후에는 하단 탭 4개(오늘·길 안내·코스 찾기·번역)로 모든 걸 한다. 편집 모드는 없고, 항목을 누르면 할 수 있는 일이 아래 시트로 올라온다.

```
여행 설정(S-01, 4단계) → 일정 생성(S-02, 빠르게·균형·알뜰 3안)
                              ↓
하단 탭 4개: [오늘 S-03] [길 안내 S-06] [코스 찾기 S-10] [번역 S-08]
  오늘 → 스팟 시트(S-04: 시간·순서·바꾸기·빼기) → 추천 시트(S-05: 대체·사이 들르기·남는 시간·대체 코스)
  길 안내 → 전체 화면 지도(S-07)
  코스 찾기 → 크리에이터 코스 상세(2단계, 기능 플래그)
  번역 → 크게 보여주기
하루 끝 → 코스 평가(S-09) → 다음 날 일정 다시 계산(S-02 로직)
바꾸거나 넣으면 자동 조정이 돌고, 무엇이 바뀌었는지 문장으로 알려준다.
```

코스 평가는 하루 마지막 장소에서 "도착했어요"를 누르면 오늘 탭에 나타나고, 제출하면 다음 날 일정이 다시 계산된다. 여행 설정은 오늘 탭 위쪽 도시·일수 버튼으로 언제든 다시 연다.

| 화면 ID | 화면 | 진입 |
| --- | --- | --- |
| S-01 | 여행 설정 (4단계) | 첫 실행, 오늘 탭 상단 "도쿄 · 3일" |
| S-02 | 일정 생성 결과 (3안 비교) | S-01 완료 |
| S-03 | 오늘 일정 | 탭 "오늘" |
| S-04 | 스팟 시트 | S-03에서 장소 탭 |
| S-05 | 추천 시트 (대체·사이 들르기·남는 시간·대체 코스) | S-04, S-03의 "+ 들르기", "다른 코스 보기" |
| S-06 | 길 안내 | 탭 "길 안내", S-03 하단 버튼 |
| S-07 | 전체 화면 지도 | S-06 "크게 보기" |
| S-08 | 대화 번역 | 탭 "번역" |
| S-09 | 코스 평가 | 하루 종료 카드 |
| S-10 | 크리에이터 코스 (2단계) | 탭 "코스 찾기" |

## 3. 화면별 명세

모든 화면 공통 규칙: 화면마다 주 버튼은 하나(화면 아래 고정, 높이 56), 터치 영역 최소 44×44, 바텀시트 제목은 한 줄, 버튼 문구는 동사형, "취소" 대신 "닫기". 문장은 쉬운 존댓말 구어체("4분 뒤 열차가 와요").

### S-01 여행 설정 (4단계)

- 상단: 뒤로 버튼, "n / 4", 진행 막대 4칸. 본문 위에 큰 질문 한 줄 + 보조 문구.
- 1단계 어디로: 도시 카드 2×2 (MVP는 도쿄만 선택 가능, 나머지는 "곧 열려요" 비활성). 일수 스테퍼 1\~9일, 날짜 범위 표시. 출발일은 달력 시트로 선택.
- 2단계 누구와: 성인(최소 1)·아동 스테퍼, 동행 유형 칩(혼자/친구/연인/가족) 단일 선택.
- 3단계 취향: 8개 타일 다중 선택(맛집, 역사·문화, 골목 산책, 야경·전망, 쇼핑, 카페, 자연·공원, 사진 명소). 0개면 다음 버튼 비활성 + "하나 이상 골라주세요".
- 4단계 스타일: 하루 템포(여유 3\~4곳 / 보통 5\~6곳 / 알차게 7곳+), 1인 하루 예산(알뜰/보통/여유), 유명↔로컬 슬라이더(0\~100, 10단위), 선택 입력 "꼭 갈 곳·이미 한 예약"(장소 검색 + 예약 시각).
- 하단: 요약 한 줄("도쿄 · 3일 · 성인 2 · 취향 3개") + 주 버튼 "다음" / 마지막 단계 "일정 만들기".

인수 조건

- [ ] 각 단계 값이 뒤로 갔다 와도 유지된다
- [ ] "일정 만들기" 후 5초 안에 S-02가 뜬다 (서버 생성 p95 3초)
- [ ] 예약을 입력한 장소는 그 시각에 고정된 채 일정에 들어간다

### S-02 일정 생성 결과

- 빠르게 / 균형(추천) / 알뜰 3안을 카드로 비교: 총 이동 시간, 1인 교통비, 2인 예상 경비, 종료 시각, 노선 색 칩.
- 날짜 탭으로 일자별 미리보기. 주 버튼 "이 일정으로 시작".

인수 조건

- [ ] 3안 모두 영업시간·예약 충돌 0건 (충돌이 남으면 그 안에 경고 배지)
- [ ] 선택한 안이 이후 S-03의 기본 이동 방식이 된다

### S-03 오늘 일정 (홈)

- 상단: "도쿄 · 3일 ▾"(S-01 다시 열기), "다른 코스 보기" 버튼(S-05 대체 코스).
- 헤드라인: "오늘은 N곳을 가요" + 보조 줄(날짜 · 2인 예상 경비 · 총 이동 · 종료 시각).
- 일자 분할 버튼(1일차·2일차…).
- 다음 이동 카드(주 색 배경): 다음 목적지 이름, "HH:MM에 출발 · HH:MM 도착", 노선 색 점 + 노선·시간·요금, 대기 안내(예약·오픈까지 20분 이상 남으면 "가는 길에 들를 곳" 버튼 → S-05 사이 들르기).
- 자동 조정 카드(조정이 일어났을 때만): 제목 "일정을 다시 맞췄어요" + 바뀐 내용 문장 목록 + \[들를 곳 보기\]/\[X 빼기\]/\[되돌리기\]/\[확인\] 중 해당 버튼.
- 처음 코스와 비교 줄(바뀌었을 때만): "처음 코스보다 이동 10분 줄었어요 · 19:50 종료" + \[남는 시간 채우기\] \[처음으로\].
- 이동 방식 칩: 빠르게/균형/알뜰 (바꾸면 즉시 재계산).
- 일정 목록: 장소 행(시각, 상태 점, 이름, 보조 줄 = 체류·평점 또는 경고), 행 사이 이동 구간(노선 색 세로선, "긴자선 18분 · ¥180", 경로 한 줄, \[+ 들르기\]). 빼고 난 빈 구간에는 "빈 자리에 넣을까요?" 인라인 추천 3곳.
- 하루가 끝나면 다음 이동 카드 대신 "오늘 일정을 다 마쳤어요" + 주 버튼 "오늘 코스 평가하기".
- 주 버튼: "길 안내 시작" → S-06.

인수 조건

- [ ] 장소를 빼거나 넣거나 시간·순서를 바꾸면 1초 안에 시간·경로·경비가 다시 그려진다 (오프라인에서도 앱 엔진으로)
- [ ] 영업시간·예약 충돌이 있으면 해당 행 보조 줄이 빨간 문구로 바뀐다
- [ ] 자동 조정이 바꾼 내용은 항상 문장으로 보여주고 "되돌리기"로 조정 전 상태가 된다

### S-04 스팟 시트

- 제목(장소 이름 한 줄), "HH:MM – HH:MM · 유형 · 요금", \[닫기\].
- 충돌 경고(빨강), 대기 안내(청록, 누르면 S-05 사이 들르기).
- 팁 박스(노랑), 평점·후기 수, 후기 키워드 칩, 대표 후기 1개.
- 머무는 시간 −/+ (15분 단위, 최소 15분, 최대 240분).
- 2×2 버튼: ↑ 앞으로 / ↓ 뒤로 / 다른 곳으로 바꾸기(S-05 대체) / 일정에서 빼기.
- 예약 가능 장소: 주 버튼 "입장권 예약 · ¥2,500" 또는 "16:40 예약 확인하기".

인수 조건

- [ ] 시트를 연 채로 시간·순서를 바꾸면 시트 내용과 뒤 목록이 함께 갱신된다
- [ ] "일정에서 빼기"는 시트를 닫고, 빈 구간에 인라인 추천을 띄운다

## 5. 일정 엔진 알고리즘

엔진은 입력이 같으면 결과가 항상 같은 순수 함수 묶음이다. 서버(Python)와 앱(TypeScript)에 같은 규칙으로 구현하고, 같은 테스트 케이스(JSON 픽스처)로 두 구현의 결과가 일치하는지 검증한다. 프로토타입 캔버스의 B안·C1 일정 화면 코드에 이 로직의 동작하는 예시가 있다.

### 5.0 상수 (설정 파일로 분리)

| 이름 | 값 | 의미 |
| --- | --- | --- |
| SLOT\_MIN | 5 | 도착 시각을 5분 단위로 올림 |
| DAY\_END | 21:30 | 하루 종료 목표 시각 (사용자 설정 가능) |
| FIXED\_LATE\_TOL | 10분 | 예약 시각보다 이만큼까지 늦어도 허용 |
| OPEN\_WAIT\_MAX | 90분 | 오픈 전 대기가 이보다 길면 문제로 표시 |
| WAIT\_HINT\_MIN | 20분 | 이 이상 대기가 생기면 "사이에 들를 곳" 안내 |
| WALK\_ONLY\_KM | 1.4 | 이 거리 이하는 도보 (경로 거리 기준) |
| WALK\_CHEAP\_KM | 2.6 | 알뜰 모드 도보 허용 거리 |
| TAXI\_CMP\_KM | 6 | 빠르게 모드에서 환승 구간 택시 비교 시작 거리 |
| TRIM\_STEP | 15분 | 체류 단축 단위 |
| TRIM\_FLOOR | max(30분, 원래 체류의 50%) | 체류 단축 하한 |
| PERMUTE\_MAX | 6 | 순서 전수 탐색 최대 장소 수 (넘으면 2-opt) |

### 5.1 일정 계산 `compute(day)`

입력: 장소 순서, 장소별 체류(기본값 또는 사용자 변경), 출발 시각, 이동 방식, 지연(구간 인덱스·분).

1. t = 출발 시각. 각 장소 i에 대해:
2. i > 0이면 구간(i−1 → i) 경로를 고른다(5.3). t += 이동 시간 + 해당 구간 지연. 총 이동·교통비 누적.
3. t를 SLOT\_MIN 단위로 올림 → 도착 시각 arrive.
4. 고정 예약이 있으면: t < 예약 시각이면 대기 = 예약 − t, 시작 = 예약 시각. t > 예약 + FIXED\_LATE\_TOL이면 문제 `late`.
5. 예약이 없으면: t < 오픈 시각이면 대기 = 오픈 − t, 시작 = 오픈 시각. 대기 > OPEN\_WAIT\_MAX면 문제 `open`.
6. 문제가 없고 시작 + 체류 > 마감 시각이면 문제 `close`.
7. 끝 = 시작 + 체류. t = 끝.

출력: 행 목록(장소 행: arrive, wait, start, end, issue / 구간 행: 경로, 지연), 총 이동, 교통비, 입장료·식비 합, 종료 시각, 문제 수.

### 5.2 일정 생성 `generate(trip)`

1. **후보 점수:** 장소마다 score = 0.5 × 취향 일치도(사용자 취향 벡터와 장소 태그 벡터의 코사인) + 0.3 × 평점 정규화 + 0.2 × 유명도 적합도(슬라이더 값과 장소 유명도 등급 1\~5의 거리). 예약 입력 장소는 무조건 포함.
2. **하루 장소 수:** 여유 4, 보통 6, 알차게 7 (식사 장소 포함).
3. **날짜별 묶기:** 상위 후보를 위치 기준 k-평균(k = 일수)으로 묶고, 묶음마다 상위 N곳 선택. 휴무일인 장소는 그 날 묶음에서 제외.
4. **식사 배치:** 맛집·시장 유형 1곳을 12:00±60분, 저녁 유형 1곳을 18:30±60분 시간창에 둔다.
5. **순서:** 시간창이 있는 외판원 문제(OR-Tools 라우팅, 시간창 = 영업시간·예약·식사 창). 이동 시간 행렬은 OTP로 구한다. 해가 없으면 평점 낮은 장소부터 하나씩 빼고 다시 푼다.
6. **3안:** 같은 순서 결정 과정을 이동 방식 빠르게/균형/알뜰로 각각 돌려 3안을 만든다.

### 5.3 구간 경로 선택

기본은 OTP 질의다. 앱이 오프라인이거나 OTP가 실패하면 역 그래프 근사로 계산하고 결과에 `estimated: true`(화면에 "예상")를 붙인다.

| 모드 | OTP 질의 | 근사 규칙 (오프라인) |
| --- | --- | --- |
| 균형 | 거리 ≤ WALK\_ONLY\_KM면 도보, 아니면 대중교통 최단(환승 1회 선호) | 같은 노선을 공유하면 직통, 아니면 두 노선이 만나는 환승역 경유, 없으면 "환승 2회" |
| 빠르게 | 대중교통 최단, 환승 구간이 TAXI\_CMP\_KM 넘으면 택시와 비교해 빠른 쪽 | 위와 같음 + 택시 시간 = 8 + 2.4 × km |
| 알뜰 | 거리 ≤ WALK\_CHEAP\_KM면 도보, 아니면 운임 최소 | 위와 같음 |

근사 시간: 도보 = 경로 km × 1000 / 75 (분), 직통 = 9 + 1.9 × km, 환승 1회 = 14 + 2.0 × km. 경로 km = 직선 거리 × 1.3. 근사 운임은 도시별 운임표 구간값을 쓴다.

### 5.4 자동 조정 `autoAdjust(day, cur)`

장소를 넣거나 빼거나, 순서·체류·이동 방식이 바뀌거나, 지연이 들어올 때마다 실행한다. cur = 지금 있는 장소 인덱스(이미 다녀온 곳과 지금 있는 곳은 건드리지 않음).

1. compute. 문제(late/open/close) 0건이고 종료 ≤ DAY\_END면 끝. 지연이 있었다면 "N분 지연은 예약 전 대기 시간으로 흡수돼요" 또는 "뒤 일정이 N분씩 밀렸어요"를 알린다.
2. **순서 재배치:** cur 뒤 장소들의 순열(≤ PERMUTE\_MAX, 넘으면 2-opt)을 계산해 문제 수가 줄어드는 순서를 고른다. 문제 수가 같으면 종료 초과 해소 → 이동 시간 짧은 순.
3. **체류 단축:** 아직 `late`나 `close`가 있으면, 그 장소 이전(close면 그 장소 포함)의 예약 없는 장소 중 체류가 가장 긴 곳을 TRIM\_STEP씩 줄인다 (TRIM\_FLOOR까지). 종료 초과만 남으면 cur 이후 전체에서 줄인다.
4. **남은 문제가 `open`(오픈 전 대기 과다)뿐이면:** 빼지 않고 "오픈까지 N분이 비어요" + 그 구간 "사이 들르기" 시트를 제안한다.
5. **그래도 남으면:** 예약 없는 장소 중 평점이 가장 낮은 곳 빼기를 제안한다(자동으로 빼지는 않음).
6. 바뀐 내용을 문장으로 만든다: "순서를 바꿨어요: A를 3번째로", "B 체류 80분 → 50분", "조정 후 20:30 종료 · 예약과 영업시간 모두 맞아요". 조정 전 상태를 보관해 "되돌리기"를 제공한다.

### 5.5 후보 점수 (대체 · 사이 들르기 · 남는 시간)

후보 c를 구간 g에 넣어 compute한 결과로 점수를 매기고, 낮은 순 상위 3개를 보여준다. 남는 시간 모드는 모든 구간 g에 넣어 보고 가장 좋은 자리를 쓴다.

```latex
\text{score}(c, g) = \Delta_{\text{move}} + 60 N_{\text{new}} + 80 I_{\text{hours}} + 45 I_{\text{late end}} - 6 r_c - 25 I_{\text{same type}} - 20 I_{\text{absorbed}}
```

- Δmove: 넣은 뒤 총 이동 − 넣기 전 총 이동 (분)
- N\_new: 새로 생긴 문제 수, I\_hours: 후보 자체가 영업시간 밖, I\_late end: 종료가 DAY\_END를 넘음
- r\_c: 후보 평점, I\_same type: (대체 모드) 뺀 장소와 같은 유형, I\_absorbed: 종료 시각이 그대로(대기 시간 안에 들어감)
- 후보 풀: 그날 묶음(5.2-3) 반경 안의 미선택 장소 + 대체 모드에서는 원래 코스 장소. 배지: absorbed → "기다리는 시간 활용", same type → "비슷한 곳", Δmove ≤ 10 → "가는 길", 실내 → "실내".

### 5.6 평가 반영 규칙 (MVP)

| 입력 | 다음 날 재생성에 반영 |
| --- | --- |
| 이동이 길었어요 | 하루 이동 상한 −20% (기본 1시간 30분 → 1시간 10분) |
| 일정이 빡빡했어요 | 하루 장소 수 −1, 장소 사이 여유 10분 추가 |
| 여유로웠어요 | 하루 장소 수 +1 허용 |
| 로컬 스팟 좋았어요 | 유명↔로컬 슬라이더 +15 |
| 사람이 너무 많았어요 | 유명도 1\~2 장소는 오전 시간창 우선, 슬라이더 +10 |
| 대기 줄이 길었어요 | 예약 가능 장소는 예약 버튼 먼저 노출 |
| 장소 좋아요 / 별로 | 그 장소 태그 가중치 +0.1 / −0.1 |
| 별점 ≤ 2 | 다음 날은 오늘과 다른 유형 비중 상향 |
| 정확도 "달랐어요" | 그날 구간을 검증 큐에 등록 (운영 확인) |

별점 ≥ 4이고 익명 공유에 동의한 코스는 (취향 유형 × 도시 × 코스) 단위로 집계해 2단계 추천 랭킹(F-26)에 쓴다.

**OTP 운영 메모**

- 도쿄 그래프 = ODPT·JR·사철 GTFS 묶음 + 간토 지역 OSM 추출본. 빌드는 별도 잡, 서비스 인스턴스는 메모리 8GB 이상.
- API는 `leg_cache`(15분 버킷)로 OTP 호출을 줄인다. 일정 생성 시 소요 시간 행렬(장소 × 장소)은 병렬 질의 후 캐시.
- OTP 장애 시 5.3 근사 규칙으로 응답하고 `estimated: true`를 붙인다.

## 11. 개발 단계 (Claude Code 작업 순서)

약 13주, 7단계로 진행한다. 각 단계는 완료 기준을 통과한 뒤 다음으로 넘어간다. 기간은 1인 개발 + Claude Code 기준 추정치다.

| 단계 | 기간 | 완료 기준 |
| --- | --- | --- |
| P0 기반 세팅 | 1주 | docker compose로 DB·OTP·API 헬스체크 통과 |
| P1 데이터 | 2주 | OTP 닛포리→시부야 경로 응답, 장소 300곳 검수 |
| P2 일정 엔진 | 2주 | 공통 픽스처 50개에서 Python·TS 결과 일치 |
| P3 API | 1.5주 | API 통합 테스트 통과, 재계산 p95 300ms |
| P4 앱 일정 화면 | 3주 | S-01~S-05 도쿄 3일 시나리오 E2E 통과 |
| P5 길 안내·번역·평가 | 2.5주 | S-06~S-09 하루 완주 시나리오 E2E 통과 |
| P6 출시 준비 | 1.5주 | 내부 테스터 10명 도쿄 실사용, 치명 버그 0건 |

**Claude Code에 주는 작업 지시 (단계별)**

1. **P0 기반 세팅**
   - 1장 모노레포 구조 생성, pnpm 워크스페이스 + Python uv 프로젝트.
   - docker-compose: PostgreSQL 16 + PostGIS, Redis, OpenTripPlanner 2, API.
   - CI: 린트, 타입 검사, pytest, Jest. `packages/ui-tokens`에 9장 토큰.
   - 이 PRD를 `/docs/PRD.md`로, 프로토타입 시안 링크를 `/docs/design.md`로 둔다.
2. **P1 데이터**
   - ODPT·JR 등 도쿄 GTFS 수집 스크립트 → stops, lines, stop\_lines 적재.
   - OSM 간토 추출본 + GTFS로 OTP 그래프 빌드 잡.
   - 장소 300곳 시드(CSV → places, place\_hours, place\_tags), LLM 태깅 배치는 검수 큐로.
   - 프로토타입 도쿄 3일(14곳 + 후보 15곳)을 테스트 픽스처로 먼저 넣는다.
3. **P2 일정 엔진**
   - `services/engine`: compute, route(OTP + 근사), autoAdjust, suggest, generate (5장 그대로).
   - `packages/engine-ts`: 같은 함수 포트(generate 제외, 경로는 캐시된 구간 + 근사).
   - `/engine-fixtures/*.json` 공통 테스트: 지연 흡수, 체류 단축, 예약 지키기, 오픈 대기, 빼기 제안, 대체·사이 들르기 순위.
4. **P3 API**
   - 7장 엔드포인트, 게스트 인증, leg\_cache, 스냅샷·되돌리기, 버전 충돌 409.
   - OpenAPI 스키마에서 앱용 TypeScript 클라이언트 자동 생성.
5. **P4 앱 일정 화면**
   - Expo Router 탭 4개, S-01\~S-05. 상태는 Zustand(화면) + TanStack Query(서버).
   - 내 변경은 engine-ts로 먼저 그리고 서버 응답으로 덮어쓰기. 오프라인 묶음 저장.
   - Maestro E2E: 설정 → 생성 → 빼기 → 빈자리 추천 넣기 → 되돌리기.
6. **P5 길 안내·번역·평가**
   - S-06 (단계, 다음 열차, MapLibre 지도 접기·펴기·전체 화면), S-08 문장 카드·TTS, S-09 평가 + 다음 날 반영.
   - 출발 알림, 운행 이상 배너(ODPT 운행 정보).
7. **P6 출시 준비**
   - 제휴 딥링크, 분석 이벤트, 개인정보·위치 약관, 스토어 등록(EAS Build/Submit), 내부 테스트.

**작업 규칙**

- 각 단계 시작 전에 이 문서의 해당 장을 다시 읽고, 바꾼 결정은 `/docs/decisions.md`에 날짜와 함께 남긴다.
- 엔진 상수(5.0)는 코드에 하드코딩하지 않고 설정 파일로.
- 화면 문구는 3장 문장을 그대로 쓰고 i18n 키로 분리.
- 2단계 기능(크리에이터 코스, 웹, 후기 쓰기, 오사카)은 MVP 완료 전에 만들지 않는다.

## 13. 글로벌 확장과 세계여행

구조는 처음부터 전 세계를 지원하게 만들고, 출시는 도시별로 연다. 나라·도시마다 데이터 품질이 다르다는 점은 사용자에게 미리, 그리고 화면 곳곳에서 계속 알린다. 여러 나라를 고르면 전체 경로와 나라별 일수를 먼저 짜고, 그 안에서 기존 하루 일정 엔진으로 세부 계획을 만든다.

### 13.1 데이터 품질 사전 고지

**도시 등급 (cities.data\_tier)**

| 등급 | 화면 표시 | 기준 | 제공 기능 |
| --- | --- | --- | --- |
| 정밀 안내 | 청록 배지 "정밀 안내" | 실시간 포함 GTFS, OTP 그래프 운영, 검수 장소 300곳 이상, 영업시간 검수율 90% 이상 | 전체 기능 |
| 기본 안내 | 회색 배지 "기본 안내" | 정적 GTFS 또는 상용 길찾기 API, 장소 150곳 이상 | 일정·자동 조정·길 안내 (실시간 지연 없음, 탈 칸·출구 없음) |
| 참고용 | 주황 배지 "참고용" | 상용 API 추정, 장소 자동 수집 위주, 검수 낮음 | 일정 초안·도시 간 이동. 모든 구간 "예상" 표시 |

등급은 배치 작업이 기준을 자동 계산하고 운영자가 승인한다. 등급 기준값은 설정 파일로 둔다.

**고지 위치와 문구**

1. **첫 실행 안내 (1회, 확인 필수, 도시 고르기 단계에서 바텀시트로 표시, "등급은 어떻게 정해지나요?"로 다시 열기):** "교통·영업시간 정보는 나라와 도시마다 데이터 품질이 달라 실제와 다를 수 있어요. 중요한 일정은 출발 전에 현지 정보를 한 번 더 확인해 주세요." + \[자세히 보기\] (도시 등급 설명 화면).
2. **여행 설정 도시 카드:** 도시마다 등급 배지. 기본·참고 등급을 고르면 카드 아래 한 줄 "이 도시는 교통 정보가 예상치일 수 있어요".
3. **일정·길 안내:** 기본·참고 등급 도시에서는 화면 상단 얇은 배너 "기본 안내 도시 · 시간은 예상이에요" (닫으면 그 여행 동안 숨김). 구간마다 "시간표" / "예상" 배지 유지 (5.3).
4. **장소 시트:** "영업시간 확인일 2026.10.12" 같은 검증일과 \[정보가 달라요\] 제보 버튼.
5. **약관·도움말:** 데이터 출처 목록, 정확도 한계, 면책 조항. 법률 검토 대상.

인수 조건

- [ ] 첫 실행 안내에 동의하지 않으면 일정 생성으로 넘어가지 않는다
- [ ] 기본·참고 등급 도시의 모든 구간에 "예상" 배지가 붙는다
- [ ] 등급이 바뀌면(예: 기본 → 정밀) 다음 앱 실행 때 배지가 바뀐다

### 13.2 세계여행 (여러 나라·도시)

**입력 (S-01 확장)**

- 1단계에서 나라·도시를 여러 개 고른다(검색 + 추천 조합). 출발 도시(예: 인천)와 귀국 도시를 따로 지정.
- 전체 일수 또는 출발·귀국 날짜, 도시 간 이동 선호(비행기 / 기차·버스 우선 / 상관없음), 순서 고정 여부.
- 2\~4단계(인원·취향·스타일)는 전체 여행에 한 번만 받고, 도시별로 덮어쓸 수 있다.

**거시 계획 엔진 `planTrip(trip)` (5장 앞에 실행)**

1. **도시 순서:** 출발·귀국 도시를 양 끝에 고정하고, 도시 간 이동 시간·비용 행렬로 최단 순서를 구한다(도시 10개 이하는 전수 탐색, 넘으면 근사). 사용자가 순서를 고정했으면 생략.
2. **도시 간 이동 추정:** 같은 나라·인접 도시는 기차·버스(데이터 있으면 실제 시간표), 그 외는 항공 예상치(거리 기반 비행시간 + 공항 이동·수속 3시간). 가격은 범위로만 보여주고 \[항공권 검색\] 제휴 링크로 넘긴다. 결과는 항상 "예상".
3. **일수 배분:** 도시별 하루 최소 1일 + 남은 일수를 (취향에 맞는 후보 장소 점수 합) 비율로 나눈다. 비행 4시간 이상인 날은 이동일(반나절 일정). 귀국편은 마지막 도시 다음 날로 잡고 전체 일수에 포함한다(예: 4+3+4+5일 + 귀국일 = 17일), 시차 3시간 이상이면 도착 다음 날 오전을 여유 있게.
4. **도시별 세부 일정:** 배분된 날마다 5.2 일정 생성을 돌린다. 이동일은 오전에 출발 준비·공항 이동, 도착 후 숙소 근처 가벼운 일정 1\~2곳.
5. **재계산:** 도시 일수 ±1, 도시 순서 변경, 도시 추가·삭제 시 1\~4를 다시 돌리고, 바뀐 도시의 일정만 새로 만든다. 지난 날짜와 확정 예약은 건드리지 않는다.

### 13.3 글로벌 공통 고려사항

- **지역 규제:** 중국은 허가받은 현지 지도 업체와 좌표계(GCJ-02) 변환이 필요하고, 한국은 정밀 지도 반출 제한으로 국내 지도·길찾기 API가 필요할 수 있다. 개인정보는 EU(GDPR) 등 지역 규정에 맞춰 동의·저장 위치를 정한다. 출시 국가마다 법률 검토.
- **시간·통화:** 모든 일정 시각은 도시 현지 시간대, 서머타임 처리, 금액은 현지 통화 + 원화 환산(환율 일 1회 갱신).
- **공휴일:** 나라별 공휴일 데이터를 넣어 휴무·혼잡을 반영.
- **언어:** UI는 한국어 우선, 문장 카드는 나라 언어별로 만들고 원어민 검수.
